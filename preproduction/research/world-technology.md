# Wizards on a Boat — world technology research

Research date: 16 September 2026. This is a preproduction recommendation, not an implementation or benchmark report. No engine, add-on, or model has been installed for this research. Final engine/add-on versions should be pinned after the concept-art review and a small compatibility test on this laptop.

## Recommended direction

Use a sparse heightfield terrain add-on for ordinary islands, modular meshes for caves/buildings/sky islands, and a replaceable ocean layer. Start with an existing Gerstner ocean implementation and compare it against an existing FFT implementation on the actual laptop. The reference board's bright cobalt water, broad readable swells and broken ivory foam depend as much on shading and composition as on wave simulation complexity.

Generate a bounded, seeded archipelago first. The request needs procedural variety, but does not require an infinite world. Keep the generation architecture chunk-aware so world size can grow later. Generate the island's destinations and traversable routes before dressing it with trees, rocks and buildings. Reuse Godot navigation and proven terrain/ocean code; reserve custom work for the game's island rules, styling and multiplayer interactions.

Terrain3D's documented regions span 64–2048 samples per side; the default is 256. Only allocated regions consume terrain RAM/VRAM, while unallocated background has no generated collision. Its documented region grid is 32 × 32, so choose the region scale against the intended archipelago size rather than treating it as limitless streaming storage. Runtime loading/unloading and generation scheduling remain our responsibility. [Terrain3D region model](https://terrain3d.readthedocs.io/en/stable/docs/introduction.html)

Terrain3D documents Vulkan Forward+, Vulkan Mobile and Compatibility support. That gives us a useful fallback if the laptop struggles with Forward+. Renderer compatibility is a separate decision from the ocean: compute-driven FFT water requires a RenderingDevice renderer and will not work unchanged in Compatibility. [Terrain3D renderer support](https://terrain3d.readthedocs.io/en/stable/docs/platforms.html), [Godot compute requirements](https://docs.godotengine.org/en/stable/tutorials/shaders/compute_shaders.html)

[Repository](https://github.com/tessarakkt/godot4-oceanfft), [development configuration](https://github.com/tessarakkt/godot4-oceanfft/blob/devel/project.godot) |

One FFT buoyancy fork explicitly downloads a displacement map to the CPU periodically and only samples its first cascade. That is a concrete warning against assuming any buoyancy fork automatically matches all visible waves. GPU readback latency and CPU/GPU disagreement must be checked before basing gameplay on it. [Fork implementation notes](https://github.com/Lucactus22/GodotOceanWaves_bouyancy)

**Proposed adaptation:** define one `OceanSurfaceQuery` contract for height, normal and water velocity at a world location and simulation time. Start by reusing a small Gerstner wave set for both rendering and buoyancy. Account for horizontal Gerstner displacement when querying world-space height; simply evaluating the original undeformed coordinates can produce a mismatch. Ship physics must consume authoritative time and parameters, independent of the camera-following visual mesh. Add stylized small wave detail only where it cannot visibly undermine the boat's contact with the surface.

The art board calls for white lace-like foam, not photorealistic refraction everywhere. Prioritize broad crest foam, shoreline bands, clean shallows/deep-water color separation, a convincing horizon and controlled glitter. Treat wakes and spell splashes as local effects. A wind spell applying an impulse to a sail does not need a fluid simulation of the entire ocean.

## Runevision: what was inspected and what transfers

The user's [July 2026 post](https://blog.runevision.com/2026/07/supercharging-my-procedural-mountain.html) was inspected (also accessible through the [July archive](https://blog.runevision.com/2026/07/?m=0)). It is a video companion page with links to the author's framework, erosion work and progression research. Its FAQ explains that some tree popping occurs when terrain LOD changes tree density; this is a useful reminder that object population and terrain LOD must be coordinated. The embedded video itself was not watched or transcribed during this pass.

**LayerProcGen** separates contextual generation into deterministic layers with declared spatial dependencies. It is a C# framework, ships with Unity integration, and is licensed MPL-2.0. The framework manages generation dependencies; it is not a complete terrain algorithm or a Godot plug-in. A Godot adaptation can reuse the architecture without promising a direct drop-in port. Importing its code should preserve and review its license obligations separately from our own code. [Author's overview](https://runevision.com/tech/layerprocgen/), [source](https://github.com/runevision/LayerProcGen)

The most directly relevant path technique is documented in the author's [natural terrain paths article](https://blog.runevision.com/2016/03/note-on-creating-natural-paths-in.html): penalizing total height change alone does not discourage a short steep climb. A superlinear slope penalty favors gentler routes. The author supplies an implicit coordinate graph and a linked [terrain pathfinder implementation](https://github.com/runevision/LayerProcGen/blob/main/Samples/TerrainSample/Scripts/Generation/TerrainObjects/TerrainPathFinder.cs). Our route planner should also enforce maximum grade, clearance, shore access and building entrances as hard constraints. Those extra constraints are our proposed adaptation, not claims about his demonstration.

## Oskar Stålberg and the linked video

The English auto-generated transcript of **“How One Guy FIXED Procedural Generation” by Game Dev Buddies** was exported and inspected. This is the creator's reconstruction and interpretation of Stålberg's methods, not direct testimony from Stålberg. The full video was not viewed. [Supplied video](https://www.youtube.com/watch?v=Y19Mw5YsgjI)

| Transcript timestamp | Relevant method described by the creator |
|---|---|
| [4:04](https://www.youtube.com/watch?v=Y19Mw5YsgjI&t=244s) | Offset a dual grid by half a cell; define land/water at corners so authored pieces can contain both concave and convex bends. |
| [6:31](https://www.youtube.com/watch?v=Y19Mw5YsgjI&t=391s) | Randomly choose among compatible model variants to reduce repetition. |
| [7:21](https://www.youtube.com/watch?v=Y19Mw5YsgjI&t=441s) | Use bounds handles and normalized vertex positions to deform pieces with the grid. |
| [8:16](https://www.youtube.com/watch?v=Y19Mw5YsgjI&t=496s) | Start with hexagonal patches, triangulate, merge selected triangle pairs, subdivide into quads and relax the resulting grid. |
| [10:15](https://www.youtube.com/watch?v=Y19Mw5YsgjI&t=615s) | Match neighborhood patterns to substitute special pieces spanning multiple tiles. |
| [11:03](https://www.youtube.com/watch?v=Y19Mw5YsgjI&t=663s) | Distinguish player-guided construction from automatic island generation; mention model synthesis/WFC without teaching that solver here. |

Primary corroboration comes from the [original WFC repository](https://github.com/mxgmn/WaveFunctionCollapse), which links Stålberg's work and describes his combination of WFC, marching cubes and irregular grids for Townscaper. It also records a Bad North heuristic favoring navigability. The repository explains that local constraints can still reach contradictions. Stålberg's [interactive Wave demonstration](https://oskarstalberg.com/game/wave/wave.html) is available, though the research browser exposed only its loading shell. His original [Bad North conference talk](https://www.youtube.com/watch?v=0bcZb-SsnrA) is a useful follow-up viewing source, not a transcript used here.

**Suitability:** use artist-authored pieces with compatible edges to preserve the reference style while creating variety. A mildly irregular grid can help harbors feel grown rather than stamped. This is especially promising for quay walls, stairs, terraced villages, ruined courtyards and dungeon dressing. It is less suitable as the sole planner for a large island with required boss access and progression guarantees. Local geometric adjacency does not itself guarantee a playable journey.

**Our adaptation:** pilot this technique on a bounded harbor or ruin district. Define canonical corner/edge sockets, reserve entrance and path cells, and select art variants using stable tile IDs. Add exceptional motifs such as a lighthouse stair landing or ruined arch as larger authored assemblies. Keep door widths, tread heights and sailboat mooring clearances fixed while allowing decorative walls and cliff faces to deform. When neighboring patches are generated independently, give shared borders common ownership and coordinate keys; any relaxation must preserve those borders. These are proposed project safeguards, not properties verified from the video. The tutorial's player-editable island toy should not be assumed to supply our terrain streaming, network synchronization or progression validation.

**Proposed division of work:** a high-level graph chooses rooms, entrances, destinations and required connections. Constrained tile/mesh selection fills the assigned spaces. Optional WFC handles local variation within a bounded footprint, with a retry limit and a known-good fallback layout. Keep landmark silhouettes and critical room sequences authored enough to remain memorable. Avoid deforming collision-critical stairs and doorways until clearance has been validated.

## Proposed deterministic generation pipeline

These steps are design recommendations derived from the research, not existing game features.

1. **World manifest.** Store world seed, generator version, content version and stable island/POI IDs. Split random streams by pass and stable ID so adding a tree does not move every dungeon. Use integer logical coordinates for keys and explicit stable ordering; do not use engine object IDs or unordered iteration as generation inputs.
2. **Regional plan.** Allocate sea biome zones, island size classes, safe sailing lanes, major landmarks and sky-island altitude bands. Reserve the starter island, harbor approach and an early exploration route. Keep global planning data compact; ocean space does not need dense terrain data everywhere.
3. **Island form.** Generate a coast mask, macro elevation, ridges, coves and beach shelves. Add bounded detail after the silhouette works. Reject or repair islands that cannot accommodate their required content. Reserve the shop, hearthstone arrival pad and spawn clearance before decoration.
4. **POI graph.** Choose dock/beach entry, secondary landing areas, visible landmarks, dungeon entrance and any boss arena. Give each POI a footprint, entrance sockets, altitude preferences, clearance and encounter budget. Guarantee an ordinary route to the intended early objectives.
5. **Paths.** Connect required POIs first; add occasional loops and optional branches. Route over slope-aware cost fields with hard grade/clearance checks. Grade the terrain into terraces or switchbacks where appropriate, place a bridge only if valid supports exist, then resample the final path to detect blocked segments. Smooth paths only inside a verified traversable corridor.
6. **Structures.** Place modular buildings/ruins using footprint and doorway constraints. Use bounded graph grammar/WFC for variation. A dungeon's reward room must be reachable without needing the very spell component rewarded inside it. Caves enter through heightfield holes into separate mesh interiors.
7. **Navigation.** Produce collision and navigation from the same final geometry. Use per-island or per-zone navigation regions; link stairs, bridges, ladders and scripted traversal explicitly. Keep sea-creature steering, walking navigation and sky flight volumes distinct.
8. **Ecology.** Apply biome, depth/altitude, time-of-day, rarity and encounter rules after geometry is valid. Keep creature population caps separate from spawn probability. Decoration must preserve path corridors and combat space.
9. **Validation and persistence.** Check spawn-to-shop, spawn-to-dock and entry-to-objective reachability; minimum ship draft clearance; overlaps; safe hearthstone arrival; biome coverage; progression dependencies. Save altered inventories, destroyed props and encounter state as authoritative deltas associated with stable IDs.

The Godot navigation API can bake from prepared source data asynchronously. SceneTree parsing still occurs on the main thread, and detailed visual mesh reads may stall rendering. Prefer simplified collision or generated triangle arrays. Navigation chunks need overlapping source bounds and border handling so seams connect. These details should be designed into the pipeline before runtime generation is expanded. [Godot navigation documentation](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationmeshes.html)

For dynamic behavior, regenerate trails when the island plan changes, and update local navigation when spells move an obstruction or destroy a bridge. Keep dependency records so only affected areas need rebuilding. Temporary small debris can use avoidance; a blocked doorway or removed bridge changes connectivity and needs an explicit navigation update. The server should publish those connectivity changes consistently to all players.

## Sky islands, multiplayer and memory

**Sky islands:** use a separate island scene with a generated/authored walkable cap, modular cliff skirt, underside rock masses and its own collision/navigation. This allows ocean islands beneath the same horizontal coordinates. The user requires a swimmable waterfall on every sky island as the normal access route. Reserve its source, continuous water column, accessible lower approach and safe upper exit during generation; verify ascent before adding vegetation or geometry that could block it. Limited breath must not make this required route depend on the future Air Bubble spell. Flat-sail wind-powered boat hovering is a future skill-based alternative. Clouds can hide distant underside transitions, but should not hide navigation failures.

**Multiplayer:** generate a versioned manifest on the host/server and have clients verify world checksums. The server owns ship forces, spell impacts, loot rolls and persistent world changes. Seeded world geometry does not imply deterministic multiplayer rigid-body physics. Replicate authoritative ship state with prediction/interpolation appropriate to the later networking design. Use interest regions around crews so distant creatures and physics props sleep. Distant clients must receive the same biome/time rules without every client simulating every mob.

**Initial laptop budget policy:** measure available system RAM and dedicated/shared GPU memory separately before choosing numeric budgets. Limit concurrent generation jobs; keep only nearby detailed islands, navmeshes, foliage and active bodies resident; use low-detail silhouettes at sailing distance. Reuse materials/atlases and modest texture resolutions. Keep shader compilation/model generation out of live play sessions. Avoid loading Blender, ComfyUI and the running game together during memory-sensitive tests. These are proposed controls, not performance guarantees.

**After art approval, a small comparison scene should decide the stack:** one boat, one walkable island, shoreline foam, the wind-into-sail interaction and two connected clients. Compare exported builds as well as editor runs. Record average and worst-frame times, generation spikes, RAM/VRAM peaks, shore contact, wave/boat alignment, navmesh seams and reconnect behavior. Run a bounded seed set for connectivity and starter-island invariants. Select the lightest water configuration that preserves the approved art direction. No FPS or memory result has been measured yet.

## Art requirements implied by the system

- Islands need readable shore/landing silhouettes, a visible destination and at least one believable route connecting them.
- Buildings need modular wall, roof, quay and stair pieces with consistent doorway/step dimensions; landmark towers may be unique.
- Dungeon sheets should show entrance, connector, arena and reward space, not only atmospheric vistas.
- Sky-island sheets must show undersides and arrival points as well as the top surface.
- Ocean art should include calm, sailing and storm states plus a shoreline close-up; gameplay wave silhouettes must remain readable around a small wizard and sailboat.

The next commitment is visual approval. Technology selection remains provisional until these research candidates have been run on the user's laptop.
